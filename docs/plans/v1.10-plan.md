# ShoeDZ v1.10: Shared Till & Safe Updates, plus a roadmap for what comes after

**Audience:** the AI coding agent implementing this plan, and the owner reviewing it.
**Read first:** [`AGENTS.md`](../../AGENTS.md). All of its rules apply: small tasks, verification commands (§2.1), side-effects table (§4.3), invariants (§4.4), migrations (§4.8), tests (§5), and no local tags or force pushes.
**Starting point:** v1.9.0 plus the v1.8–v1.9 non-feature review fixes (branch `fixes/v1.9-release-pipeline`, HEAD `3f544c1`).

---

## 0. Why this release

- **Updates are risky.** Three of the last four release lines shipped regressions straight to the pilot store. The desktop app migrates the store's database at startup with **no snapshot first** (`desktop/python/shodz_desktop/server.py::_run_migrations`). v1.10 makes updates survivable before it adds more behaviour.
- **The till needs to be shared.** The pilot store wants several staff to use one till without logging out and back in. Doing that safely needs three things first:
  - **Sale attribution:** `CashSession.get_open_session` (`backend/apps/sales/models.py` ~line 308) falls back from the cashier to the branch to **any open session in the tenant**, so quick switching would scatter sales across Z reports.
  - **Real locking on SQLite:** `select_for_update()` does nothing there, and the v1.5–v1.9 fixes rely on it.
  - **Numbering that can't collide:** receipts (`RC-YYYYMMDD-####`, `sales/serializers.py` ~line 591) and session numbers (`CashSession.save`, ~line 298) are computed as max + 1.
- **The year-end count needs shelf scopes.** The store's first closing is about six weeks away. Stocktakes can only be scoped by brand or category (`StocktakeSession.scope_brand` / `scope_category`), while products already have shelf locations (`ProductLocation.location`). Group A can ship ahead of the rest as a v1.9.x patch.
- **Help sits too far from the screens.** The manual is complete and the Help button opens the right chapter (`frontend/src/lib/helpLinks.ts`), but there is no in-context explanation next to a feature and no "what changed" after an update.

## 1. Decisions (defaults already chosen; the owner can change them before work starts)

| ID | Decision | Default |
|---|---|---|
| D10.1 | Drawer mode | `StoreSettings.drawer_mode` ∈ {`personal`, `shared`}, default **`personal`** (today's behaviour). In `shared` mode, one open session per **till**, and each sale records who rang it. In `personal` mode, switching user also switches session. |
| D10.2 | Who can switch by PIN | Any active cashier or manager **who has signed in with their password on this till at least once**. **Never the owner**: owner access always needs the password. |
| D10.3 | PIN length for switching | 4 or 6 digits, as today (`User.set_pin`). After 5 wrong PINs for a user on a till, that user must sign in with their password. |
| D10.4 | Idle auto-lock | Optional store setting, **off** by default. When on (e.g. 5 minutes), the till returns to the switch screen and keeps any cart as a parked sale. |
| D10.5 | Cart on switch | In `shared` mode the cart stays on the till. In `personal` mode the current cart is parked automatically (using the existing `HeldSale`) before switching. |
| D10.6 | Update delay | Owner setting: **install stable updates 3 days after release** (0 = immediately). "Update now" stays available in Settings → Desktop. |
| D10.7 | Django upgrade | Upgrade **Django 5.0.6 → 5.2 LTS** to get SQLite `transaction_mode="IMMEDIATE"`. **Ask the user before changing any dependency** (AGENTS.md §4.12). If refused, skip 10.6 and document `select_for_update` as a known no-op on desktop. |
| D10.8 | Number format | New receipts get a till code: `RC-YYYYMMDD-C1-0001`. Session numbers become per-till counters: `Z-C1-0042`. **Existing documents keep their numbers.** Invoice numbering is unchanged (already a locked counter). |
| D10.9 | Help text source | Short hints live **in the manual sources**, next to the section they summarise. The build generates the hint files, so help text has one source in three languages. |
| D10.10 | Sync outbox | Stop writing `SyncOutbox` rows by default (setting `SYNC_OUTBOX_ENABLED = False` on desktop). Existing rows are purged in batches by the scheduler. The model stays. |

## Group A: Year-end count by shelf (can ship first, as a v1.9.x patch)

### 10.1 Stocktake scoped by shelf location
- **Change:**
  - Add `StocktakeSession.scope_location` (CharField, blank; migration).
  - When creating a session with a location scope, include the variants of products whose `ProductLocation.location` matches **for the session's branch** (case-insensitive, prefix match, so `A` covers `A1`, `A2`), alongside the existing brand/category filters.
  - Products with no location for that branch can be included through an explicit "no location" scope, so nothing is silently left out.
  - Add the location filter to the stocktake creation UI (`StocktakePage.tsx`). Put new UI in a separate component (AGENTS.md §4.9).
- **Tests:** a location scope picks only matching products for the branch; the "no location" scope; combining it with the brand scope.

### 10.2 Printable count sheets per shelf
- **Change:**
  - Add an endpoint returning an A4 count sheet for a session (optionally one location). It lists product, reference, colour and a row of sizes with empty boxes, and **no expected quantities** (a blind count).
  - Print it through the existing `printerConfig.ts` A4 helpers, not `window.open` + `document.write`.
  - Escape all data (`escapeHtml`).
- **Tests:** the sheet contains every in-scope variant and no expected quantity.

### 10.3 Several counters in one session
- **Change:**
  - Add `StocktakeItem.counted_by` (FK user, nullable).
  - Scan and count endpoints update `counted_qty` atomically (`F("counted_qty") + n`, then re-read), so two people scanning the same shelf don't overwrite each other.
  - The session screen shows progress per location and per counter.
  - Applying the session still requires a manager (role map from v1.5).
- **Tests:** concurrent increments from two users both count; `counted_by` is recorded.
- **Done when:** the owner can split the year-end count by shelf, print sheets, have two staff count in parallel and apply once.

## Group B: Safe updates

### 10.4 Snapshot before migrating
- **Change:** in `server.py::_run_migrations`, when the migration plan is not empty:
  - take a snapshot with the existing SQLite online backup (`apps/core/desktop/backup.py`), named `pre_update_<oldVersion>_to_<newVersion>_<timestamp>.sqlite3`;
  - store it outside the normal rotation, keeping the **last 3** pre-update snapshots;
  - **if the snapshot fails, do not migrate.** Show the error on the splash screen with a "Diagnostic" action, and stop.
- **Record the version:** write `app_version_last_migrated` in the desktop `config.json` (`backup.py::save_desktop_config`).
- **Tests:** a unit test of the "should snapshot" helper; a test that `_run_migrations` calls the snapshot before `migrate` (mock both).

### 10.5 Automatic data rollback when a migration fails
- **Change:** if `migrate` raises:
  1. Close all DB connections.
  2. Move the half-migrated `db.sqlite3` (plus `-wal` / `-shm`) to `backups/failed_update_<timestamp>/`.
  3. Copy the pre-update snapshot back into place. Reuse the file-swap logic in `apps/core/desktop/restore.py::apply_pending_restore_if_needed`; extract a shared helper instead of duplicating it.
  4. Exit with a **distinct exit code** that `desktop/main.js` recognises.
- **Electron side:** on that exit code, show an "Update failed: your data was restored" screen with three actions:
  - **Retry;**
  - **Create diagnostic bundle** (v1.6 feature);
  - **Download the previous version:** a link to the GitHub release of `last_good_version`, see 10.6.

  Do not restart in a loop.
- **Tests:**
  - a backend test with a deliberately failing migration in a temp data dir: data is restored and the failed copy is kept;
  - the user verifies the Electron screen by hand on Windows.

### 10.6 Post-start self-check and "last good version"
- **Change:**
  - Add an endpoint `GET /api/v1/desktop/selfcheck/` (localhost only, no auth beyond the existing desktop token pattern). It checks:
    - `PRAGMA quick_check` = ok;
    - no unapplied migrations;
    - one template renders;
    - the media dir is writable.
  - After the window loads and the self-check passes, Electron writes `last_good_version` in `config.json`. If the self-check fails, show the same failure screen as 10.5, without restoring data.
- **Tests:** the self-check fails when a migration is unapplied (mock) and passes on a migrated test DB.

### 10.7 Delayed stable updates
- **Change:**
  - In `desktop/main.js`, set `autoDownload = false`. On `update-available`, download only if `now − info.releaseDate ≥ update_delay_days` (default 3). Otherwise schedule a re-check.
  - Settings → Desktop (owner only): the delay setting, the version available and its date, and an **"Update now"** button.
  - Prereleases stay ignored (`allowPrerelease` unset).
- **Tests:** a unit test of the "should download now" helper with injected dates.
- **Done when:** a failed migration in a test build leaves the store's data intact and shows a clear screen, and stable updates wait the configured delay.

## Group C: Real locking and collision-free numbering

### 10.8 Django 5.2 LTS and SQLite IMMEDIATE transactions (needs approval, D10.7)
- **Change:**
  - Upgrade Django in `backend/requirements-desktop.txt` and `backend/requirements.txt` to the latest 5.2.x.
  - Check compatibility of `djangorestframework`, `djangorestframework-simplejwt`, `django-filter`, `django-unfold`, `drf-spectacular` and `django-cors-headers`. Bump only what's required, and list every change in the report.
  - Set `DATABASES["default"]["OPTIONS"]["transaction_mode"] = "IMMEDIATE"` in `config/settings/desktop.py`, keeping `timeout`.
- **Concurrency test:** add one that uses a **file-based** SQLite test database (an in-memory test DB can't show this). Two threads creating sales concurrently must not oversell the last pair or duplicate a number.
- **Done when:** the full suite passes on 5.2, the CI import smoke test passes on x64 and ia32, and the concurrency test passes.

### 10.9 One locked counter for all document numbers
- **Change:**
  - Generalise `InvoiceCounter` (`apps/invoicing/models.py`) into a core `DocumentCounter(tenant, prefix, period_key, last_sequence)` with a locked `next_number()`, or reuse it as is if the agent finds that simpler.
  - Use it for receipt numbers (`RC`, `RES`) and cash-session numbers, replacing max + 1.
  - Apply the D10.8 formats to **new** documents only.
  - Backfill: counters start from the current max per prefix and period, via an idempotent data migration.
- **Tests:** 100 sequential numbers have no gaps or duplicates; concurrency test as in 10.8; old numbers unchanged.

## Group D: Shared till and quick account switching

### 10.10 Till identity
- **Change:**
  - **Model** `Till(TenantScopedModel)`: `branch`, `code` (e.g. `C1`, unique per branch), `name`, `is_active`.
  - On first run, or on the first start after upgrading, create `C1` for the headquarters branch and store `till_id` in the desktop `config.json`.
  - The frontend sends an `X-Till-Id` header from the desktop config (exposed through `desktop_meta`).
  - Add `CashSession.till` (FK, nullable) and `HeldSale.till` (FK, nullable); migration.
  - Owner-only Till management in Settings (only one till matters until v1.11).
- **Tests:** first-run creation is idempotent; an unknown till ID is rejected.

### 10.11 Session lookup follows the drawer mode
- **Change:** `CashSession.get_open_session(tenant, user, branch, till)`:
  - **`personal` mode:** the user's open session only;
  - **`shared` mode:** the till's open session;
  - **remove the "any open session in the tenant" fallback.** With no session found, sales return 400 "open a cash session". Today that fallback attributes sales to the wrong drawer.
  - Every caller uses this helper: `create_sale`, `add_payment`, `collect_layaway`, cancellations and refunds, cash movements.
  - Add `StoreSettings.drawer_mode` (migration, default `personal`).
- **Tests:** both modes; no fallback across users in personal mode; the shared session is picked by till.

### 10.12 Quick switch: backend
- **Change:**
  - **Model** `TrustedTillUser(till, user, last_password_login_at)`, written on every successful **password** login that carries `X-Till-Id`.
  - **Endpoint** `POST /api/v1/core/auth/switch/` `{user_id, pin}` returns a new JWT pair. Rules:
    - the target is active, in the same tenant, **not owner** (D10.2) and trusted on this till;
    - the user has a PIN set;
    - the PIN matches.
  - **Failure handling:** count failures per (till, user) with an atomic cache increment (`cache.add` / `cache.incr`). After 5 failures, mark that user as "password required" on this till until their next password login (D10.3).
  - **Audit:** every switch and failed attempt writes an `AuditLog` entry (`action="switch"`, from-user, to-user, till).
  - **Rate limit:** add the endpoint to the throttles in both `base.py` and `desktop.py`.
- **Tests:**
  - success;
  - owner refused;
  - untrusted user refused;
  - wrong PIN counted, lockout after 5, cleared by a password login;
  - audit row written;
  - cashier → 403 on any other user's data after the switch.

### 10.13 Quick switch: frontend
- **Change:**
  - In `Topbar.tsx`, add an avatar strip or menu of users trusted on this till, each opening a PIN pad. Write a new `SwitchUserModal.tsx`; don't extend `ManagerPinModal`.
  - Add a keyboard shortcut, after checking `useGlobalShortcuts.ts` and the `before-input-event` handler in `main.js` for conflicts, and list it in `ShortcutsModal.tsx`.
  - **On switch:** store the new tokens, clear user-specific react-query caches (`queryClient.clear()`, then refetch), apply the new user's language and role guards, and handle the cart per D10.5.
  - **Idle lock (D10.4):** when enabled, show the switch screen after the configured idle time.
  - All text through `t()` in fr, ar and en; RTL; dark mode.
- **Tests:** vitest for the cache reset and the cart handling helper.

### 10.14 Sales by user inside a shared session
- **Change:**
  - The Z report (`sales/services/z_report.py`) and the daily report add a breakdown by `Sale.cashier`: count, total, payments by method, refunds, discounts approved by PIN. This works in both modes.
  - Print it on the thermal Z report as an optional section.
- **Tests:** two users selling in one shared session get correct per-user totals that add up to the session totals.

- A separate "seller" field distinct from the user who rang the sale. Add it only if the owner confirms the store pays commission on sales that someone else rings up (open question 2).

# Roadmap: what comes after v1.10

Each step has **entry criteria**. Don't start a step until they're met; each one builds on the safety of the previous.

## v1.11: Second till on the same LAN (no sync)
- **What:** one PC hosts the database and backend. Other PCs run the app in **client mode**, with no embedded Python, pointing at the host. There's one database, so there's nothing to sync.
- **Builds on v1.10:** till identity (10.10), IMMEDIATE transactions (10.8), counters with till codes (10.9), drawer modes (10.11), safe updates (Group B).
- **Main work:**
  - **Electron:** a client mode; pairing with the host by a one-time code; the host stores paired tills.
  - **Backend:** bind to the LAN interface **only when pairing is enabled**; a Windows firewall rule from the installer; CORS limited to paired tills.
  - **Security review before exposing anything beyond 127.0.0.1:**
    - every `AllowAny` endpoint;
    - `desktop_shutdown` must fail closed when `SHUTDOWN_TOKEN` is unset;
    - desktop-only endpoints (backups, restore, diagnostics, self-check) must stay host-local;
    - the PDF bridge stays per machine.
  - **Printing:** printer settings per till, not per database.
  - **Updates:** host and clients must run the same version; a client refuses to work against a different host version.
  - **Backups:** host only.
- **Entry criteria:** v1.10 has run in the store for at least 2 weeks with no data incident, and a customer actually needs a second till.

## v1.12: Owner dashboard, one-way
- **What:** the till pushes **daily summaries** (sales, payments by method, Z gaps, stock alerts, cheques due) to a small hosted read-only page. Nothing comes back down, so store data can't be damaged.
- **Builds on:** the outbound message queue and claim-based sending from v1.9 (`apps/notifications/services/outbound.py`), and the Telegram summary builders.
- **Main work:**
  - a minimal hosted service: authentication per owner, storage of summaries only (no customer personal data), retention;
  - a push channel in the outbound queue;
  - opt-in in Settings.
- **Entry criteria:**
  - a **hosting and licensing decision** (who pays, how accounts are created);
  - the dormant cloud code reviewed or removed. The first audit found open endpoints and tenant gaps there, so this is a fresh, small service, not a revival of the old SaaS mode.

## Later: Multi-branch stock
- **What:** each branch keeps its own database. Branches exchange **transfer documents**: a `StockTransfer` exported by the sending branch and imported (or pushed through the v1.12 channel) by the receiving one. Each document is applied once, keyed by its ID.
- **Why not general sync:** stock is already an append-only ledger, and transfers are already modelled. Exchanging documents keeps each database authoritative for its own sales, money and numbering.
- **Entry criteria:** a real customer with two branches that share stock, and v1.12 in place if the exchange should be automatic.

## Only if the above is not enough: two-way sync
- **Prerequisites before it can even be designed:**
  - numbering that is unique across devices; v1.10's till codes cover receipts and sessions, but invoices would need a branch or device prefix too;
  - client and supplier balances recomputed from ledgers instead of cached running totals;
  - a written conflict policy **per model**: which side wins, and what happens to stock and money on conflict;
  - a hardened server.
- **Note:** the old `SyncReceiverView` ("last write wins" on any model) must not be revived.
- **Entry criteria:** documented demand that multi-branch transfers (above) cannot meet.

## Smaller items queued for later releases
- **Shelf-label reprint queue:** after bulk price or tier changes, list the products whose printed shelf labels are now wrong and print them in one action.
- **"Served by" field and commission report:** depends on open question 2.
- **Licensing decision:** gates v1.12 and anything else involving the cloud.
